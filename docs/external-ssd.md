# External SSD: supported paths and verification

Data migration is deliberately separate from `install.py`. It depends on the host OS, browser/desktop permission model, encryption key handling and independent backups. A one-command universal SSD move would be unsafe. This guide applies to Codex without Docker or Colima; follow the VM/container checks only if those services are part of the data you choose to move.

## Preflight

1. Confirm the real running executable, client-selected model/effort, process parent, `CODEX_HOME`, `CODEX_SQLITE_HOME`, open files, app support/cache and destination mount identity. On macOS use `diskutil info` plus `lsof`; on Linux use `findmnt` and `/proc/<pid>/fd`; on Windows use PowerShell `Get-Volume` and process/file-handle inspection. If tools are missing, stop rather than claim independence.
2. Inspect free bytes on the data volume, destination space, encryption state, hardware/SMART availability and any filesystem warning. A healthy fsck is not a hardware-life test. If filesystem checks disagree, investigate offline without unmounting beneath the operator; repeat only after a causal change.
3. Inventory Git remotes and dirty/untracked/ignored worktrees. GitHub only covers confirmed remote objects, not Codex conversations, credentials, database volumes or local work. Back up the rest on independent storage. Keep credentials outside the public repo; use a private recovery method for the encryption passphrase.
4. Determine who uses the original Codex home. Do not move its root while an independent gateway or other process holds an open coordination DB there. On this Mac, opencodex uses an internal `~/.codex` file and cannot depend on an absent external drive.
5. Inventory optional Codex plugins and their actual package, cache and helper paths before moving them. A plugin cache symlink may point through `CODEX_HOME` to the SSD. Record both the visible path and physical target. For Browser or Computer Use, record whether the current conversation exposes their interaction capability; an open sidebar tab alone does not prove it can be controlled.

## Cutover and proof

1. Record exact sources, destinations, timestamps, symlink targets and rollback paths. If Docker/Colima is in scope, also record running containers, ports and restart policies. Prepare application-consistent SQLite backups; use PostgreSQL logical dumps or cleanly stopped volume copies only when those data exist, and prove an isolated restore. Do not tar active PostgreSQL files.
2. Read local copy-tool docs before choosing flags. Preserve symlinks, ownership, ACL, xattrs and sparse VM images where possible. Full-file checksums and path inventories, not mtimes, establish content parity. Treat timeout, short copy or socket file as incomplete.
3. Prove the operator continues after closing GUI. Gracefully close GUI/app-server and other writers, including a VM if one is in scope; perform the final copy, compare, then atomically switch only known paths. Keep originals under dated rollback names. If Docker is involved, do not use `docker system prune`, `colima delete`, volume removal or reset a database.
4. Verify CLI login, GUI account, existing active and archived conversations, manually selected models and worktrees. If Docker/Colima was moved, start exactly the previously running containers, mount every real target of guest bind paths, and verify volume hashes/DB queries/health, ports, context/socket and open VM images. Do not send a test turn into an owner's conversation.
5. Protect startup without the SSD: detect the correct UUID and unlocked encrypted volume **before** writing. Test a missing-drive simulation for every entry point, including the actual official Dock/start-menu icon and auto-start jobs. On platforms where an official launcher cannot be intercepted safely, do not claim fail-closed behavior; choose a guarded launcher or obtain a vendor-supported solution. Never change the signed app bundle or turn off platform security.
6. Finish encryption (not just start it), keep secrets in a local password manager outside the disk, and retain all source originals until the owner confirms GUI behavior and independent backups are proven. Measure reclaimed physical space with `df`/volume free bytes only after approved cleanup.

## Browser and Computer Use after cutover or upgrade

The bundled Browser plugin may run through a separate helper process. After moving the plugin cache or updating Codex, verify the selected Browser package version and resolve every configured helper path through symlinks to its physical target. If the active Browser service uses a package under the relocated cache, the trusted service entry and trusted code paths must cover that exact package and its real target. Do not use a broad trust directory merely to make an error disappear, disable path validation, copy browser cookies, or edit the signed app bundle.

Configuration on disk is only the intended state. Compare the relevant **running helper process** environment with the current `config.toml`, without printing unrelated environment variables or secrets. If it still has paths from before the cutover, finish or safely pause active Codex tasks, then restart the app through its approved launcher. Restarting only a browser tab does not reload an already running helper's environment. Do not kill arbitrary helper PIDs while other tasks use them.

Finally, use the Browser plugin's documented client in a conversation where that capability is available: list or select a tab, read its visible state, and perform one harmless interaction in the in-app browser. `open_in_codex` proves only that a tab can be displayed. A standalone Playwright session uses a separate profile and does not prove control of the signed-in sidebar tab. Computer Use may intentionally refuse to target the Codex app; do not bypass that boundary. If the current conversation does not expose Browser even after a verified restart, report that session-level limitation instead of claiming the SSD migration is repaired.

If the old Browser client still fails but the **same conversation** exposes the bundled `mcp__cua_repl.js` tool, use its supported in-app browser surface instead of repeating restarts. On the first call run only `await cua.getState();` and read the returned browser inventory and API documentation. Bind only to a browser/tab explicitly present in that fresh snapshot whose `codexSessionId` exactly matches the current conversation. Select it using the exact browser and tab IDs from that snapshot, or an explicit tab mention supplied for this conversation; do not select by URL, a remembered ID, or a guessed `iab` default. Keep user tabs intact. After selection, read back the returned tab identity and visible page state, confirm they still match the intended current-conversation tab, then test one harmless interaction. If the session metadata is absent or mismatched, the target is missing, or more than one candidate matches, stop without falling back to URL matching, another conversation, or a global session/socket. Never hard-code a `codexSessionId`, REPL socket, port, or session singleton. Tool availability and tab binding are conversation-specific: if `mcp__cua_repl.js` is absent or a safe exact match cannot be established, report that limitation. A successful check proves only current-conversation access; do not infer that another conversation is correctly bound or that the SSD migration caused or repaired the issue. Before claiming multi-conversation reliability, repeat the harmless check independently in at least two conversations and verify in each that the fresh session metadata and selected browser/tab IDs belong to that conversation. Do not extract or transfer cookies, switch to a separate Playwright profile, or use desktop Computer Use to evade an app safety refusal.

### A readable tab can still reject interaction

After binding the correct conversation, test a harmless action with an observable result, such as an in-page anchor changing the URL. A successful tool return without that change is not a pass. Refresh the accessibility state once after a detached-element error; do not keep retrying the same click or switch to a different conversation.

If a pre-existing tab remains readable but clicks have no effect, compare it with one temporary tab created through the **already verified browser ID**. Use a public, non-sensitive page without copying login data or unsaved form contents. Verify the new tab's identity, perform the same harmless action, and close only that temporary tab afterwards. Preserve the user's original tab. A reload of the original is appropriate only when it cannot discard unsaved work; it is not a guaranteed repair.

On 2026-09-27, one current-conversation check on macOS app 26.924.22138 reproduced this distinction: the existing tab could be read and navigated explicitly but its clicks had no visible effect, including after a reload; a temporary tab in the same browser changed its anchor after a click. This establishes a tab-specific interaction failure, not its root cause or a fix for every conversation. New-tab success must not be reported as recovery of the original tab.

If desktop logs report `untrusted-process-ancestry`, treat that as a separate rejected helper connection, not evidence of wrong-session routing. Do not bypass the rejection with injected session metadata, a copied socket, broader trust roots or modified signed application code. Prefer the host-provided, current-conversation browser capability when available. A manually registered `mcp_servers.node_repl` with pinned app/package paths can coexist with that native tool and drift after upgrades; inventory its consumers before changing or disabling it. Do not assume that changing global configuration refreshes helpers already running in other conversations.

## Restore

Stop new GUI writers and any VM included in the move; verify the rollback manifest, reverse only the exact atomic path switches, restore original service policies and start precisely the original running set. Recheck login, one session and the official app; recheck databases only when they were in scope. Retain the original internal archive of older conversations. If the SSD is unavailable, preserve the originals and notify the owner; do not generate a fresh empty profile.

This procedure is a portable decision/verification contract. Platform-specific file operations require a separate implementation and real-host tests; no script here silently migrates the machine.
